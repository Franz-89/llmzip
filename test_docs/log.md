## 2026-10-16

- NUC technologies DTOs (`NucApiDTO`, `NucCommandQueueApiDTO`, `NucLogRequestApiDTO`, `NucLogApiDTO`) now ship `statusRendered` / `typeRendered` straight from the model's `renderStatus()` / `renderType()` badge; the `statusTone` / `typeTone` fields and their DTO-side colour switches are gone. Documented in `/apis.md` (payload rule 2).
- Exposed the NUC section to `sapienscore-technologies`, which now shows it as a pure window (owner picker, then everything live from here). Reads: owner-scoped `/v1/technologies/{nuc,nucLog,nucLogRequest,nucCommandQueue,nucSystemMetric}/...` plus `nuc/option`; writes: new route group `/v1/technologies-command/nuc/{create,update,allow-installation,init,command-queue/create,command-queue/cancel}` answered by `App\Controller\Admin\API\V1\Nuc\NucController` through `TechnologiesResponder` (no per-resource `Technologies*Manager` adapters: they only forwarded to `NucActionManager`). NUC credentials and key files stay off the wire. Every NUC read and command, from the back office and from technologies, now goes through the single entry point `NucVerifier` (`forCurrentUser()` / `forOwner()`; reads via `verifyNuc()`) + `NucActionManager` (commands), so the action and its `nuc-action` audit line are identical for both; the back-office controllers, `Nuc::getList()` uses it too (back-office responses unchanged; the command-queue and system-metric fragments, which had no access check, now have the back office's location check, and creating a NUC now requires access to its location). Documented in `/apis.md`.

## 2026-10-15

- `/v1/technologies/location/list` accepts an optional `data.idOwner` filter (`TechnologiesLocationManager::buildWhere()`): only locations whose organization has that `owner` are returned. One deployment can serve several owners, and `sapienscore-technologies`' Semaphore automation launch form (owner -> core or location -> all/selected locations -> playbook) needs exactly one owner's locations. Absent or < 1 means no owner filter, so existing callers are unaffected. Documented in `/apis.md`.

## 2026-08-28

- Writes in `OutboundProductRequestManager` and `OutboundShippingManager` now send one named array instead of a flat list of `addData()` keys: the envelope carries `{data:{productRequest:{…}}}` / `{data:{shipping:{…}}}`, named after the object being written. Reads keep their flat keys — the split is write/read, nothing else, so `createDraft`/`updateDraft`/`submit`/`approve`/`reject`/`returnToDraft`/`reportIssue` nest while `listRequest`/`getRequest`/`listStatusHistory`/`listShipping` do not. `OutboundRequestBuilder` needed no change — `addData()` already takes any value — and `idOperator` still rides in the path, outside the payload. `createDraft`/`updateDraft` merge `$draftData` into the array in the same order as the flat version merged it, so caller-supplied keys still win over the actor defaults; the repeated actor label moved into `renderActorName()`. Companion change on `sapienscore-technologies`: each API controller takes the array back out of the envelope itself and reads it as a plain array, leaving `InboundOperatorContext` untouched — see its own log. There is no flat-payload fallback on either side, so the two must be deployed together.
- Moved the `/v1/technologies` read-API managers from `App\Manager\API\Admin\Technologies\` to `App\Manager\API\Admin\SapienscoreTechnologies\Inbound\`, so the inbound half of the sapienscore-technologies integration sits next to its existing `SapienscoreTechnologies\Outbound\` half and mirrors the `SapiensClient\{Inbound,Outbound}` layout. `AbstractTechnologiesReadManager`, `TechnologiesLocationManager` and `TechnologiesReadResponder` moved unchanged apart from their namespace; `LocationController`'s imports and the resource checklist in `/apis.md` follow. No route, endpoint or payload change.

## 2026-08-27

- Moved every product-request call onto `sapienscore-technologies`' new operator-scoped `/api/v1/operator/{idOperator}/…` surface. New `TechnologiesOperatorResolver` discovers owner -> `idOperator` via `POST /api/v1/operator/resolve` and memoises the result only for the current request, so each owner is resolved at most once per request while changes on technologies become visible on the next request. `OutboundRequestBuilder` gained `setIdOperator()`, `SapienscoreTechnologiesApiTarget` gained `renderApiPath()` + `usesEnvelope()`, and `OutboundSendRequestSapienscoreTechnologies` stopped flattening `data` — the v1 body is now the `{data:{…}, officialToken}` envelope, while the docs surface deliberately stays flat because `APIDocumentationController` reads its params straight off the request. Every method on `OutboundProduct/ProductRequest/ShippingManager` takes `int $idOperator` first and no longer sends `owner`; `listShipping` moved to `product/request/shipping/list`. The admin screens carry `{idOperator}` in their own routes (`/product-request/detail/{idOperator}/{idProductRequest}` and friends), with `ProductRequestViewDTO::setIdOperator()` carrying it from the list render into every link; `redirectDetail()` keeps the old two-segment detail URL working for existing bookmarks and queued notifications. `/list`, `/new`, `/create`, `/preview/grouping` and `/resolve/address` stay unscoped, each for a documented reason.
- Documented the read-only `/v1/technologies` read API in `/apis.md`: auth, the shared `list`/`one` shape, the allow-list and rendered-value payload rules, and the checklist for adding a resource on both sides.

## 2026-07-03

- Fixed `productRequest.addDestination()` in `productRequest.js` reusing a destination group number already present on the page after a removal (`this.groupIndex` alone was not a reliable source of the next number). New `nextGroupIndex()` cross-checks the in-memory counter against the highest `productRequestDestination-N` id actually rendered right now and returns one past whichever is higher, so a freshly added destination can never collide with one still on the page even if the counter itself ever desyncs.
- Fixed a select2 memory/state leak in the product-request wizard: `productRequest.removeDestination()` only did `$('#productRequestDestination-N').remove()`, which doesn't tear down select2's own instance registry for the warehouse/product pickers inside it. Add → remove → add a destination without ever picking a warehouse could leave the new destination's warehouse picker showing a warehouse selected on its own. Fixed by calling `.select2('destroy')` on every `select.select2-hidden-accessible` inside the destination box before removing it from the DOM. Also converted the country field from a free-text input to a proper dropdown via `CountryManager::renderListOption()` (alpha3-coded, matching `AddressDTO`'s stored format) in `create.phtml`, `edit.phtml`, and `destinationBlock.phtml`; `productRequest.js`'s `applyResolvedAddress()` now `.trigger('change')`s the country select after a programmatic `.val()` so select2's displayed label stays in sync.
- Fixed the create-draft path so a new product request is always created — one per supplier/entity group — instead of the tech side silently reusing/appending to an existing open draft found by owner+entity. `updateDraft` already required `idProductRequest` and only ever touches that one request; no change needed there. Renamed `warehouseId` to `idWarehouse` everywhere in the product-request feature (form fields, DOM ids, DTO/array keys, `ProductRequestDraftDTO::setGroupWarehouseId()` → `setGroupIdWarehouse()`) to match the codebase's `idX` naming convention. Fixed `destinationBlock.phtml` passing `$address['warehouseId'] ?? 0` (always 0, since the warehouse id was never part of `$address`) instead of the actual `$idWarehouse` variable to `WarehouseTemplateRender::renderListOption()`'s `selected` arg — the warehouse/location dropdown now pre-selects correctly when editing an existing draft. Added cross-group warehouse exclusivity in `productRequest.js` (`refreshWarehouseOption()`, called on add/remove destination, on address resolution, and on page load): a warehouse/location already chosen for one destination group is now disabled in every other group's picker. Touched: `App/DTO/ProductRequest/ProductRequestDraftDTO.php`, `App/Controller/Admin/ProductRequestController.php`, `App/Manager/ProductRequest/ProductRequestManager.php`, `App/Manager/API/Admin/SapienscoreTechnologies/Outbound/OutboundProductRequestManager.php`, `public/assets/adminlte/js/src/productRequest.js`, `templates/adminlte/productRequest/{create,edit}.phtml`, `templates/adminlte/productRequest/module/destinationBlock.phtml`. Companion fix on `sapienscore-technologies`: see its own log.

## 2026-07-02

- Product-request create wizard now supports multiple destinations: the form is organized in groups (group 0 = non-physical products, no shipment; groups 1..N = destination blocks with warehouse/address + physical product lines added via `productRequest.addDestination()`). A picked product is disabled in its group's picker (re-enabled on line removal) and may still be sent to other destinations. `ProductRequestDraftDTO` flattens groups into `lineDestination[]` + `listDestination` for the tech `product/request/create-draft` endpoint (which remains per-supplier-entity grouping with per-line destination addresses). Touched: `templates/adminlte/productRequest/create.phtml`, `public/assets/adminlte/js/src/productRequest.js`, `App/DTO/ProductRequest/ProductRequestDraftDTO.php`, `App/Controller/Admin/ProductRequestController.php`. New translation keys used: `product_request.label.general_section`, `product_request.label.general_section_hint`, `product_request.btn.add_destination`.
- Two lines requesting the same product for the same destination group now merge into one summed line instead of duplicating, both in the create and the new edit wizard. Enforced server-side in `ProductRequestController::mergeDuplicateProductLine()` (applied to the flattened payload from `ProductRequestDraftDTO::buildPayload()` before it is sent to the tech API), not client-side.
- Added a full draft-edit page (`GET /product-request/edit/{idProductRequest}`, `POST /product-request/update/{idProductRequest}`) replacing the old "Add Line" link (which opened a blank new-request wizard). `templates/adminlte/productRequest/edit.phtml` reuses the create wizard's markup/JS (`productRequest.js`, now with a parameterized `submitDraft(url)`), pre-filled from the draft's current lines. Since destinations aren't stored as groups server-side (only per-line `warehouseId` + `destinationAddress`), `ProductRequestController::buildEditGroup()` reconstructs groups by clustering lines that share the same warehouse+address; lines without a destination address go to group 0. The edit page is entity-scoped: `OutboundProductManager::listProduct($idContact)` restricts the product picker to the draft's own supplier (a draft's owner+entity are fixed after creation), unlike the create wizard which spans the whole catalog. New render partials `templates/adminlte/productRequest/module/lineRow.phtml` and `module/destinationBlock.phtml` (+ `ProductRequestTemplateRender::renderLineRow()`/`renderDestinationBlock()`) produce the server-rendered prefill rows/boxes; brand-new destinations added after page load still go through the existing client-side `<script type="text/template">` clone. New translation key used: `product_request.label.edit` (reuses existing `common.btn.edit`, `common.btn.save`).
- Companion change on the `sapienscore-technologies` side: added `POST /api/v1/product/request/update-draft` (`APIProductRequestController::updateDraft()` -> `ProductRequestManager::updateDraftByRequest()`), which replaces a draft's `listLine`/`destinationAddress` wholesale (unlike `create-draft`'s `upsertDraft()`, which appends to an open draft for the same owner+entity). Validates every submitted product belongs to the draft's own `idContact` and that the request is still a draft.
- Fixed a `TypeError` crash on the `sapienscore-technologies` draft detail page (`templates/adminlte/product/request/module/detail.phtml`): it called `AddressDTO::initByArray()` unconditionally, which crashed on drafts with no destination address yet (now a valid state for non-physical-only drafts under the multi-destination model), because `Helper::issetInArray()` skips mandatory-field validation when the input array is empty. Fixed by only building the DTO when `destinationAddress` has data; `addressHandler.phtml` already renders blank fields when no `addressDTO` is passed. `Helper::issetInArray()`'s empty-array short-circuit itself was left unfixed (shared helper, out of scope) — other `AddressDTO::initByArray()` callers may have the same latent issue.
